# Continuous Integration, PR Artifacts and Semver Releases

Parent spec: `specs/01-static-python-web-frozen.md` (SHIPPED, frozen 2026-09-02).
Requirements introduced here use the **1xx** range; requirements imported from
the parent keep their original identifiers (e.g. "NFR-002 from spec-01").

Version: 1.1
Last Updated: 2026-09-02
Status: READY
Owner: Federico Castañeda

## Purpose

Spec 01 shipped a static Python playground whose correctness rests entirely on
its own test suite — 30-odd Vitest units, 16 Playwright e2e specs, a contrast
audit and a performance audit — and today every one of those runs only on a
maintainer's laptop, by hand, if remembered. This spec defines the automation
that makes the suite the gate: a pipeline that runs it on every pull request
and refuses the merge on failure, publishes the built site as a downloadable
artifact stamped with the PR number so a reviewer can try the real build, and
on merge to `main` derives a Semantic Versioning bump from the merge commit,
tags it, and cuts a GitHub Release with the built site attached. The
beneficiaries are the maintainer (regressions caught before merge, releases
cut without manual steps) and reviewers (a real build to click, per PR).

## Scope

### In

- A **PR pipeline** on GitHub Actions gating merges into `main`: type check,
  Vitest units, the Playwright `chromium` project, the contrast audit and the
  performance audit.
- A **build artifact per PR**, named with a semver-legal PR suffix and uploaded
  as a workflow artifact.
- Diagnostics upload (Playwright HTML report and traces) when the gate fails.
- A **release pipeline** on push to `main`: derive the semver bump from the
  merge commit, write `package.json`, tag `vX.Y.Z`, create a GitHub Release
  with generated notes, and attach the built site as a tarball.
- Conventional-Commits validation of the PR title, since a squash merge makes
  the PR title the merge commit subject the bump is derived from.
- Least-privilege workflow permissions and pinned action versions.

### Out

- **The browser matrix** (`npm run test:matrix`, VC-055 / NFR-011 from
  spec-01). Two of its eight pinned projects (`edge-141`, `edge-140`) have no
  launchable engine on a GitHub Linux runner and would report `skipped`; a skip
  is not a pass (BR-105), so the matrix stays a local/manual criterion and CI
  makes no eight-browser claim.
- **Deployment.** Netlify continues to build and deploy from its own git
  integration, driven by `netlify.toml`. No CI job deploys anything, no Netlify
  credentials exist in this repository, and no PR preview URLs are produced.
- **The long-running and manual criteria** of spec-01: VC-059 (`RUN_LONG=1`, a
  six-minute run), VC-056 (physically disconnecting the network), VC-063
  (publishing a second deployment by hand) and VC-021's greyscale check.
- Coverage measurement and coverage thresholds.
- A maintained `CHANGELOG.md` file. Release notes live on the GitHub Release.
- Dependency update automation (Dependabot/Renovate), container publishing, npm
  registry publishing (the package is `"private": true`), and signed releases.
- Any change to the application source, to spec-01's thresholds, or to the test
  suite's contents. This spec runs the suite; it does not alter it.

## Actors

| Actor | Description | Permissions |
|---|---|---|
| Contributor | Opens a PR from a branch in this repository | Push to feature branches; cannot merge with a red gate; can download PR artifacts |
| Fork contributor | Opens a PR from a fork | Same gate; the PR run receives a read-only token and no secrets (BR-106) |
| Maintainer | Reviews and merges | Squash-merges into `main`; can edit the PR title (which becomes the release-bump input); can re-run jobs |
| PR pipeline | `.github/workflows/pr.yml`, GitHub-hosted runner | `contents: read` only |
| Release pipeline | `.github/workflows/release.yml`, GitHub-hosted runner | `contents: write` only (tag, release commit, Release) |
| Netlify | Existing external deploy integration | Reads `main`; no interaction with either pipeline |

## Functional Requirements

Priorities are MoSCoW: **M**ust, **S**hould, **C**ould, **W**on't.

### The PR pipeline

**FR-100 (M) — Trigger.**
Given a pull request whose base branch is `main`,
When it is opened, synchronized with a new push, reopened, or **edited** (a
title or body change),
Then the PR pipeline runs against the merge result of the head and base
commits, including while the pull request is a draft.
`edited` is required because FR-111 gates on the pull request *title*, which
can change without any push: without it, a PR opened with a malformed title
keeps a red required check that no contributor action can refresh.

**FR-101 (M) — Deterministic install.**
Given a pipeline run,
When it prepares the workspace,
Then it checks out the commit, activates Node.js 26.x, installs with `npm ci`
from the committed `package-lock.json`, and installs the Playwright `chromium`
browser with its system dependencies; no step resolves a dependency version
not already pinned in `package-lock.json`.

**FR-102 (M) — Type check gate.**
Given a prepared workspace,
When the pipeline runs the type check,
Then `tsc --noEmit` must exit 0, and a non-zero exit fails the run.

**FR-103 (M) — Unit gate.**
Given a prepared workspace,
When the pipeline runs `npm run test:unit`,
Then every Vitest test in `tests/unit/` must pass, and any failure fails the
run.

**FR-104 (M) — Browser gate.**
Given a prepared workspace,
When the pipeline runs the Playwright `chromium` project,
Then every e2e spec except `matrix.spec.ts` must pass — the same set a local
`npx playwright test` runs — and any failure fails the run.

**FR-105 (M) — Contrast audit gate.**
Given a prepared workspace,
When the pipeline runs `npm run audit:contrast`,
Then VC-051 and VC-071 from spec-01 must pass in both palettes, and any
failure fails the run.

**FR-106 (M) — Performance audit gate.**
Given a prepared workspace,
When the pipeline runs `npm run audit:perf`,
Then VC-053 from spec-01 must pass with its thresholds unmodified (BR-104),
its printed measurements appear in the job log, and any failure fails the run.

**FR-107 (M) — PR artifact.**
Given a PR pipeline run whose gates FR-102 through FR-106 all passed,
When the pipeline uploads the built site,
Then it uploads one workflow artifact named
`pyplay-<base-version>-pr.<pr-number>+<short-sha>` containing a single
`pyplay-<base-version>-pr.<pr-number>+<short-sha>.tar.gz` whose extracted root
is the contents of `dist/` (see *Data & Interfaces*).

**FR-108 (M) — Artifact retention and replacement.**
Given an existing artifact for a pull request,
When a new commit is pushed to that pull request,
Then the run for the new commit uploads its own artifact and the artifact of
the superseded commit is deleted, so exactly one artifact exists per open pull
request, retained 14 days.

**FR-109 (M) — Failure diagnostics.**
Given a PR pipeline run in which the browser gate, contrast audit or
performance audit failed,
When the run finishes,
Then it uploads an artifact named `playwright-report-pr.<pr-number>` containing
`playwright-report/` and `test-results/` (traces included), retained 7 days.

**FR-110 (S) — Superseded runs are cancelled.**
Given a PR pipeline run in progress for a pull request,
When a new commit is pushed to the same pull request,
Then the in-progress run is cancelled and only the newest run reports a status.

**FR-111 (M) — PR title validation.**
Given a pull request targeting `main`,
When the PR pipeline runs,
Then the pull request **title** must match the Conventional Commits grammar of
*Data & Interfaces* with a type from the accepted set, and a title that does
not match fails the run with a message naming the accepted types.

**FR-112 (M) — Merge protection.**
Given a pull request targeting `main`,
When any required check of the PR pipeline has not concluded successfully for
the head commit,
Then the pull request cannot be merged.

**FR-113 (W) — Browser matrix.**
The PR pipeline will not run `npm run test:matrix`, for the reason recorded in
*Scope → Out* and BR-105.

### The release pipeline

**FR-114 (M) — Trigger.**
Given a push to `main` (the squash-merge of a pull request, or a direct push),
When the push completes,
Then the release pipeline runs against that commit.

**FR-115 (M) — The gate runs again before publishing.**
Given a release pipeline run,
When it starts,
Then it runs FR-102 through FR-106 against the pushed commit and publishes
nothing unless all of them pass.

**FR-116 (M) — Bump derivation.**
Given the pushed commit's message,
When the release pipeline derives the version,
Then it computes the bump from that message alone per BR-100 and BR-101, and
the new version is the current version from BR-102 with that bump applied.

**FR-117 (M) — The no-release case.**
Given a pushed commit whose derived bump is *none* (BR-100),
When the release pipeline finishes,
Then it concludes successfully, creates no tag, no commit and no Release, and
its log states that the commit type produces no release.

**FR-118 (M) — Version commit.**
Given a derived version `X.Y.Z`,
When the release pipeline publishes,
Then it writes `X.Y.Z` to the `version` field of `package.json`, updates
`package-lock.json` to match, and pushes one commit to `main` with the subject
`chore(release): vX.Y.Z [skip ci]` containing only those two files.

**FR-119 (M) — Tag.**
Given a derived version `X.Y.Z`,
When the release pipeline publishes,
Then it creates the annotated tag `vX.Y.Z` on the version commit and pushes it.

**FR-120 (M) — GitHub Release.**
Given the pushed tag `vX.Y.Z`,
When the release pipeline publishes,
Then it creates a non-draft, non-prerelease GitHub Release named `vX.Y.Z` on
that tag whose body is GitHub's generated notes for the commits since the
previous tag.

**FR-121 (M) — Release asset.**
Given the Release `vX.Y.Z`,
When the release pipeline publishes,
Then it attaches exactly one asset named `pyplay-X.Y.Z.tar.gz`, built from the
same commit the gate of FR-115 passed on, whose extracted root is the contents
of `dist/`.

**FR-122 (M) — Idempotency.**
Given a release pipeline run whose derived version already exists as a tag,
When the run reaches the publishing step,
Then it makes no change to the tag, the Release or its assets, and concludes
successfully with a log line stating the version is already released.

**FR-123 (M) — Fork pull requests.**
Given a pull request opened from a fork,
When the PR pipeline runs,
Then every gate of FR-102 through FR-106 runs and the artifact of FR-107 is
uploaded, using a token with no write scope and no repository secrets.

**FR-124 (M) — Release runs are serialized, never cancelled.**
Given a release pipeline run in progress,
When a second push to `main` starts another release pipeline run,
Then the second run waits for the first to finish and then proceeds — the
in-progress run is never cancelled, and the two runs never publish
concurrently.
*A cancelled release loses a release: unlike a superseded PR run (FR-110),
whose only product is a status, an interrupted release run can leave a tag
without a Release or a Release without its asset.*

**FR-125 (M) — Stale-base recovery.**
Given a release pipeline run whose push of FR-118 is rejected because `main`
advanced after its checkout,
When the rejection occurs,
Then the run re-reads the current version per BR-102, re-derives the version
from **its own** triggering commit, and retries the push at most **3** times
with the freshly fetched `main` as its base; if the third attempt is also
rejected, the run fails, having created no tag and no Release.

## Business Rules

**BR-100 — The bump mapping.**
The bump is derived from the commit subject's Conventional Commits type and the
presence of a breaking marker:

| Commit | Bump |
|---|---|
| `feat: …` / `feat(scope): …` | minor |
| `fix: …` / `perf: …` / `revert: …` | patch |
| any type with `!` before the colon, or a `BREAKING CHANGE:` footer | major |
| `chore:` `docs:` `style:` `refactor:` `test:` `build:` `ci:` | none |

*Rationale:* the repository's history already uses this vocabulary
(`feat: …`, `fix: …`), so the bump is readable from `git log` without a
release tool's state file. *Exceptions:* none — a subject that does not match
the grammar cannot reach `main`, because FR-111 rejects it on the pull request.

**BR-101 — Breaking always bumps major, including before 1.0.**
A breaking marker produces a major bump even from a `0.x.y` version
(`0.1.0` + `feat!:` → `1.0.0`).
*Rationale:* the common alternative (breaking → minor while below 1.0) means
the version number silently stops carrying breakage information for the whole
pre-1.0 period, which is exactly when this playground's persisted-state and
worker-protocol contracts are most likely to break. One rule, always true, is
worth leaving `0.x` early. *Exceptions:* none.

**BR-102 — Git tags are the version's source of truth.**
The current version is the highest `vX.Y.Z` tag reachable from `main`, or
`0.1.0` (the value committed in `package.json` at the time of this spec) when
no such tag exists — in which case the first release is that value with the
derived bump applied. `package.json`'s `version` is a mirror maintained by
FR-118, never an input to FR-116.
*Rationale:* one authority prevents two runs disagreeing about the base
version, and makes a re-run of a failed release recover by itself.
*Exceptions:* none.

**BR-103 — Pipeline-authored commits must not retrigger the pipeline.**
The version commit of FR-118 is pushed with the workflow's `GITHUB_TOKEN` and
carries `[skip ci]` in its subject.
*Rationale:* two independent guarantees against an infinite release loop — a
push made with `GITHUB_TOKEN` does not start a new workflow run, and the
`[skip ci]` subject stops a run that some future trigger change would
otherwise start. *Exceptions:* none.

**BR-104 — Spec-01 thresholds are never relaxed for CI.**
Every numeric threshold asserted by `audit:perf`, `audit:contrast` and the e2e
suite is the value spec-01 fixed. A gate that fails because the runner is
slower than the reference profile is resolved by faster runners, a larger
runner label, or a genuine performance fix — never by editing a threshold,
adding a CI-only tolerance, or skipping the assertion.
*Rationale:* a threshold that moves to match the hardware measures the hardware
instead of the product. *Exceptions:* none.

**BR-105 — A skipped test is never reported as a pass.**
No required check may include a test that reports `skipped`. A criterion whose
engine or preconditions are unavailable on a GitHub runner stays out of the CI
scope and is named in *Scope → Out*, rather than being run into a skip that
looks green.
*Rationale:* spec-01 already refuses to stub an unavailable engine onto a
substitute; a green check that covers nothing is worse than a documented gap.
*Exceptions:* none.

**BR-106 — PR runs get no secrets and no write scope.**
Both workflows declare an explicit top-level `permissions:` block; neither uses
the runner's default permission set. The PR workflow's block is exactly
`contents: read` and it reads no repository secret. Only the release workflow,
which runs on `push` to `main` after the merge, holds `contents: write`.
The PR workflow is triggered by `pull_request` and **never** by
`pull_request_target`, which runs the base repository's workflow with a
writable token while checking out a fork's code.
*Rationale:* PR code is untrusted by construction — a fork PR can run arbitrary
build and test code — so nothing a PR run can reach may be able to tag,
release, or authenticate anywhere. `pull_request_target` is named explicitly
because it is the one trigger that grants exactly what this rule forbids, and
it is easy to reach for later when a PR job appears to "need" a token.
*Exceptions:* none.

**BR-107 — The published artifact is the tested build.**
The tarball attached to a Release is produced in the same pipeline run, from
the same commit, as the gate that passed in FR-115. No artifact is copied
between commits, rebuilt later, or promoted from a PR run.
*Rationale:* a release asset that was not the thing the suite ran against is
untested by definition. *Exceptions:* none.

**BR-108 — Third-party actions are pinned by commit SHA.**
Every `uses:` reference to an action outside this repository names a full
40-character commit SHA, with the human-readable version in a trailing comment.
*Rationale:* a moving tag such as `@v4` is a mutable dependency with write
access to the release pipeline. *Exceptions:* none.

## Non-Functional Requirements

**NFR-100 — PR gate wall clock.** A PR pipeline run with a warm npm cache
completes within **20 minutes** from trigger to final status. Each job declares
a `timeout-minutes` of at most **30**, so a hung run fails rather than
occupying a runner.

**NFR-101 — Install cost.** On a run with a cache hit on the
`package-lock.json`-keyed npm cache **and** on the Playwright browser cache,
`npm ci` plus the Playwright `chromium` install complete within **150 seconds**
combined. A run that misses either cache — the first run after a dependency
change, or after the cache's 7-day eviction — is bounded only by NFR-100, since
`playwright install --with-deps` then also installs system packages. Both
caches are therefore required, not optional (FR-101).

**NFR-102 — Release latency.** From the push to `main` to the published
Release, the release pipeline completes within **25 minutes**.

**NFR-103 — Verdict stability.** Re-running the PR pipeline on an unchanged
commit produces the same pass/fail verdict. Playwright's existing CI retry
setting (`retries: 2` when `CI` is set) is the only retry mechanism; no gate
step is wrapped in a retry loop, and `continue-on-error` appears on no gate
step.

**NFR-104 — Runner cost of the artifact.** The uploaded PR tarball and the
Release asset are each at most **30 MB** compressed (the `dist/` tree is ~22 MB
uncompressed, dominated by the 13 MB vendored Pyodide and 11 MB vendored Ruff).

## Data & Interfaces

### Files this spec adds

| Path | Contents |
|---|---|
| `.github/workflows/pr.yml` | The PR pipeline (FR-100 – FR-112, FR-123) |
| `.github/workflows/release.yml` | The release pipeline (FR-114 – FR-122) |
| `.nvmrc` | `26`, the Node.js major both workflows and local development use |

No existing file changes except `package.json` / `package-lock.json`
`version`, written by FR-118.

### Conventional Commits grammar (FR-111, BR-100)

```
<type>[(<scope>)][!]: <subject>
```

- `type` ∈ { `feat`, `fix`, `perf`, `revert`, `chore`, `docs`, `style`,
  `refactor`, `test`, `build`, `ci` }
- `scope` — optional, non-empty, no `)`
- `!` — optional breaking marker
- `subject` — non-empty after the `: `

A breaking change is signalled by `!` or by a `BREAKING CHANGE:` footer line in
the commit body.

### Artifact and tag naming

| Thing | Grammar | Example |
|---|---|---|
| PR artifact / tarball | `pyplay-<base-version>-pr.<pr-number>+<short-sha>` | `pyplay-0.1.0-pr.42+a1b2c3d` |
| Failure diagnostics artifact | `playwright-report-pr.<pr-number>` | `playwright-report-pr.42` |
| Tag | `v<X>.<Y>.<Z>` | `v0.2.0` |
| Release name | `v<X>.<Y>.<Z>` | `v0.2.0` |
| Release asset | `pyplay-<X>.<Y>.<Z>.tar.gz` | `pyplay-0.2.0.tar.gz` |

- `base-version` — `package.json`'s `version` at the head commit; the PR name
  is a semver-legal prerelease + build-metadata string, so it sorts below the
  release it precedes.
- `pr-number` — the pull request number, decimal, no padding.
- `short-sha` — the first 7 characters of the head commit SHA.

### Tarball layout

Both tarballs extract to the *contents* of `dist/`, not a wrapping directory:

```
index.html
sw.js
precache-manifest.json
_headers
assets/…
pyodide/…
ruff/…
```

### Pipeline inputs

| Input | Source | Used by |
|---|---|---|
| `github.event.pull_request.title` | GitHub event | FR-111 |
| `github.event.pull_request.number` | GitHub event | FR-107, FR-109 |
| `github.sha` | GitHub context | FR-107 short SHA |
| Pushed commit message | `git log -1 --format=%B` | FR-116 |
| Highest `vX.Y.Z` tag | `git tag --list --merged main` | BR-102 |
| `GITHUB_TOKEN` | GitHub-provided | FR-118 – FR-122 |
| `CI=true` | Runner default | Playwright `retries: 2`, `forbidOnly` |

No repository secret beyond the GitHub-provided `GITHUB_TOKEN` is required by
either workflow.

### Required checks for merge protection (FR-112)

`pr-title`, `typecheck`, `unit`, `e2e-chromium`, `audit-contrast`,
`audit-perf`, `artifact`.

## Verification Criteria

Each line is `VC-NNN: <scenario> → <observable expected result>`.

### The PR gate

- **VC-100 (FR-100):** Open a PR targeting `main`, then push a second commit to it, then convert it to a draft and push a third → a PR pipeline run exists for all three head commits.
- **VC-101 (FR-101):** Inspect a completed run's log → it reports Node 26.x, `npm ci` (not `npm install`), and a Playwright install limited to `chromium`; the run installs no package version absent from `package-lock.json`.
- **VC-102 (FR-102):** Open a PR introducing a type error (e.g. assign a `string` to a `number` in `src/main.ts`) → the `typecheck` check fails, its log shows the `tsc` diagnostic, and the PR cannot be merged.
- **VC-103 (FR-103):** Open a PR that breaks a unit invariant (e.g. change the console retention cap in `src/console-buffer.ts` from 5 000) → the `unit` check fails naming the failing Vitest test.
- **VC-104 (FR-104):** Open a PR that breaks a browser behaviour (e.g. remove the `[stderr] ` prefix from `src/format.ts`) → the `e2e-chromium` check fails naming the failing VC-numbered spec.
- **VC-105 (FR-104):** Inspect a passing `e2e-chromium` log → every spec in `tests/e2e/` except `matrix.spec.ts` reports a result, and zero tests report `skipped`.
- **VC-106 (FR-105):** Open a PR lowering a text colour token's contrast below 4.5:1 → the `audit-contrast` check fails naming the sampled element and its measured ratio.
- **VC-107 (FR-106):** Inspect a passing `audit-perf` log → each of NFR-001, NFR-002, NFR-003, NFR-004, NFR-005, NFR-007 and NFR-008 from spec-01 appears with its measured value and its threshold.
- **VC-108 (FR-106, BR-104):** Compare the thresholds asserted in the `audit-perf` job to the values in spec-01 → they are identical, and no environment variable, CLI flag or code path in the repository alters a threshold when `CI` is set.
- **VC-109 (FR-111, FR-100):** Open a PR titled `Fixes` → the `pr-title` check fails and its message lists the accepted types. Rename it to `fix: boot the worker under Vite`, touching nothing else → a new run starts from the title edit alone, with no push and no manual re-run, and `pr-title` passes.
- **VC-110 (FR-111):** Open PRs titled `feat(editor)!: drop the v1 storage key` and `chore: bump docs` → `pr-title` passes for both.
- **VC-111 (FR-112):** With one required check failing on the head commit, attempt to merge → GitHub refuses the merge and names the failing required check.
- **VC-112 (FR-110):** Push two commits to a PR three seconds apart → the first run's status is `cancelled` and only the second run reports a merge-gating status.
- **VC-113 (FR-123):** Open a PR from a fork of this repository → all seven required checks conclude, the artifact of FR-107 is present, and the run's token has no write scope (an attempted `git push` in that run is rejected).
- **VC-114 (BR-106):** Read both workflow files → each declares a top-level `permissions:` block, the PR workflow's is exactly `contents: read`, the release workflow's is exactly `contents: write`, the PR workflow references no `secrets.*` other than `GITHUB_TOKEN`, and neither workflow is triggered by `pull_request_target`.
- **VC-115 (BR-108):** Grep every `uses:` line in both workflows → each third-party reference is a 40-character hex SHA.
- **VC-116 (NFR-103):** Re-run a completed PR pipeline on an unchanged commit → the verdict matches the first run, and no gate step in either workflow file contains `continue-on-error` or a retry loop.
- **VC-117 (NFR-100, NFR-101, NFR-104):** Measure a warm-cache PR run → total wall clock ≤ 20 min, install + browser install ≤ 150 s, uploaded tarball ≤ 30 MB, and every job declares `timeout-minutes` ≤ 30.

### The PR artifact

- **VC-118 (FR-107):** Merge-gate a PR numbered 42 at head `a1b2c3d…` with `package.json` at `0.1.0` → the run's artifact list contains exactly `pyplay-0.1.0-pr.42+a1b2c3d` and `pyplay-0.1.0-pr.42+a1b2c3d.tar.gz` inside it.
- **VC-119 (FR-107):** Download and extract that tarball → `index.html`, `sw.js`, `precache-manifest.json`, `assets/`, `pyodide/` and `ruff/` are at the extraction root with no wrapping directory; serving it with COOP/COEP reaches `Python … ready`.
- **VC-120 (FR-108):** Push a new commit to PR 42 → after the new run, exactly one `pyplay-*-pr.42+*` artifact exists, its SHA suffix is the new head's, and its retention shows 14 days.
- **VC-121 (FR-107):** Open a PR whose `e2e-chromium` check fails → no `pyplay-*` artifact is uploaded for that run.
- **VC-122 (FR-109):** In that same failed run → an artifact `playwright-report-pr.<N>` exists with 7-day retention, containing `playwright-report/index.html` and at least one trace under `test-results/`.
- **VC-123 (FR-109):** In a fully passing run → no `playwright-report-pr.*` artifact is uploaded.

### The release

- **VC-124 (FR-114, FR-116, FR-118 – FR-121):** With `v0.1.0` the highest tag, squash-merge a PR titled `feat: add a run-history panel` → tag `v0.2.0` exists on a commit whose subject is `chore(release): v0.2.0 [skip ci]`, `package.json` reads `0.2.0`, and Release `v0.2.0` carries exactly one asset `pyplay-0.2.0.tar.gz`.
- **VC-125 (BR-100):** Squash-merge `fix: restore the stderr prefix` from `v0.2.0` → the released version is `0.2.1`.
- **VC-126 (BR-100, BR-101):** Squash-merge `feat!: replace the pyplay.program.v1 key` from `v0.2.1` → the released version is `1.0.0`.
- **VC-127 (BR-100, BR-101):** Squash-merge `refactor: split runtime.ts` whose body contains a `BREAKING CHANGE:` footer, from `v1.0.0` → the released version is `2.0.0`.
- **VC-128 (FR-117):** Squash-merge `docs: expand CONTRIBUTING` → the release pipeline concludes successfully, the highest tag is unchanged, no `chore(release)` commit is pushed, no Release is created, and the log states the type produces no release.
- **VC-129 (FR-115, BR-107):** Push directly to `main` a commit titled `fix: x` that fails the unit gate → the run fails, and no tag, commit, Release or asset is created.
- **VC-130 (FR-115, BR-107):** Extract the asset of a successful Release and compare it byte-for-byte with a local `npm ci && npm run build` at the tagged commit's parent tree → the file lists and contents match.
- **VC-131 (FR-119, FR-120):** Inspect the created Release → the tag is annotated, the Release is neither draft nor prerelease, its name is `vX.Y.Z`, and its body lists the commits since the previous tag.
- **VC-132 (FR-122):** Re-run the release pipeline on a commit whose derived version is already tagged → the run succeeds, the tag still points at the same commit, the Release's asset list is unchanged, and the log states the version is already released.
- **VC-133 (BR-102):** Delete `package.json`'s version drift by hand-setting it to `9.9.9` in a PR, merge a `fix:` from `v1.0.0` → the released version is `1.0.1` (derived from the tag, not from `package.json`), and the release commit rewrites `package.json` to `1.0.1`.
- **VC-134 (BR-102):** In a repository state with no `vX.Y.Z` tag, merge `feat: first feature` with `package.json` at `0.1.0` → the released version is `0.2.0`.
- **VC-135 (BR-103):** After a successful release → the `chore(release): vX.Y.Z [skip ci]` commit has started no workflow run, and no second release exists for it.
- **VC-136 (NFR-102):** Measure a successful release → the Release is published within 25 minutes of the push to `main`.
- **VC-140 (FR-124):** Squash-merge two pull requests titled `fix: a` and `feat: b` within one minute of each other, from `v1.0.0` → both release runs conclude successfully, neither reports `cancelled`, tags `v1.0.1` and `v1.1.0` both exist, each with its own Release and asset, and the second run's tag is on a commit descended from the first run's version commit.
- **VC-141 (FR-125):** Force the race by pushing an unrelated commit to `main` after a release run's checkout but before its push (e.g. hold the run at its gate) → the run reports a rejected push, retries against the fetched `main`, and publishes the version derived from its own triggering commit, not from the commit that overtook it.
- **VC-142 (FR-125):** Configure `main` so the pipeline's push can never succeed, then merge `fix: x` → the run fails after at most 3 push attempts, and no tag, no Release and no asset exist for the derived version.

### Scope boundaries

- **VC-137 (FR-113, BR-105):** Grep both workflow files → neither invokes `test:matrix`, sets `MATRIX`, nor names any `chrome-*`, `edge-*`, `firefox-*` or `safari-*` project, and no required check reports a skipped test.

## Open Questions

None. The four decisions this spec turned on — Conventional-Commits versioning
over labels or manual bumps, the PR gate's contents, GitHub Releases without a
CI-driven deploy, and the artifact naming and retention — were settled before
drafting and are stated normatively in BR-100, FR-102 – FR-106, *Scope → Out*
and FR-107/FR-108 respectively.

## Assumptions

- **A-1** Pull requests are merged into `main` with **squash merge**, so the
  merge commit subject is the (validated) PR title. GitHub's repository setting
  must have squash merge enabled with the commit message defaulted to the pull
  request title, and merge commits and rebase merges disabled — otherwise
  FR-111's validated title is not what FR-116 reads. Direct pushes to `main`
  are still handled: FR-116 reads whatever subject the pushed commit carries,
  and an unrecognized type produces no release (FR-117).
- **A-2** GitHub Actions on GitHub-hosted `ubuntu-latest` runners with the
  default free-tier concurrency is the execution environment; no self-hosted
  runner exists.
- **A-3** Branch protection on `main` is configured by a maintainer through
  repository settings, not by a file in this repository. FR-112 is verified
  against that configuration (VC-111); this spec does not create it.
- **A-4** The `dist/` build is reproducible from `package-lock.json` alone:
  `scripts/vendor-pyodide.mjs` and `scripts/vendor-ruff.mjs` copy from
  `node_modules/`, so no build step downloads from a CDN and no network access
  beyond the npm registry is needed. Verified by VC-130.
- **A-5** The GitHub-provided `GITHUB_TOKEN` with `contents: write` is
  permitted to push directly to `main` — branch protection either exempts it or
  allows the release pipeline to bypass the required checks it has just run on
  that same commit. This is a **hard prerequisite**, not a branch in the
  design: FR-118 is Must and has one shape. If the repository's settings do not
  allow it, the fix is the settings (an exemption for the release workflow's
  actor), and until then the release pipeline is expected to fail loudly at
  FR-125's third rejected push rather than to silently release without its
  version mirror. Verified by VC-142, which is exactly this misconfiguration
  observed deliberately.
- **A-6** Node.js 26.x is the supported local and CI version (the maintainer's
  machine runs v26.8.1); `package.json` declares no `engines` field and this
  spec does not add one.

## A flagged risk (not an open question)

The performance audit's thresholds — NFR-001 shell interactive ≤ 2.0 s,
NFR-002 cold runtime ready ≤ 10.0 s, NFR-003 warm ≤ 2.5 s — were measured on a
maintainer's laptop against loopback, and `tests/e2e/perf.spec.ts` explicitly
justifies them as *necessary* conditions on a link no slower than loopback. A
GitHub-hosted `ubuntu-latest` runner has substantially less CPU than that
reference profile, and booting a 13 MB Pyodide WASM runtime is CPU-bound.
`audit-perf` is therefore the check most likely to fail on hardware rather than
on a regression.

This spec keeps it as a **required** check anyway, because a performance gate
that does not gate is not a gate. BR-104 fixes the only permitted responses: a
real performance fix, or more capable runners. VC-107's requirement that every
measurement be printed next to its threshold exists precisely so the first runs
show how much headroom the runner actually has, and VC-117's wall-clock budget
will show if `audit-perf` becomes the pipeline's long pole.
